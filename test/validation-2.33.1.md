# 2.33.1 本地验证记录

验证日期：2026-10-14。环境：macOS、Chrome 稳定版（Playwright `channel: 'chrome'`）。

## 触发这一版的现场数据

用户用 2.33.0 跑整套对比，4 轮里 **3 轮整轮被限流**：

```
429 Rate limit exceeded. Limit type: requests. Current limit: 10, Remaining: 0.
```

| 轮次 | 调用失败字段数 | 实际情况 |
| --- | --- | --- |
| deepseek-chat 中文 | 7 | 只有最后一批被限流，**前面都通了** |
| 其余三轮 | 各 65 | 每一批都被打掉，**0 个字段来自模型** |

唯一真实的一轮：**deepseek-chat 中文，准确率 89% · 错填 1 · 漏答 7**，
而那 7 个漏答正好是被限流的那一批（最高学历 + 6 个英文表单字段）。

与本机 Nano 对比（同一套 71 题）：

| | 准确率 | 错填 |
| --- | --- | --- |
| Nano 中文 | 61% | 21 |
| Nano 英文 | 70% | 16 |
| **deepseek-chat 中文** | **89%** | **1** |

那唯一一个错填是「部门及岗位 → `work.dept`（标注为 `work.title`）」——
标签本身合并了部门与岗位两个概念，这更像是评测集的标注值得商量，而不是模型犯错。
**未改标注**，留给用户定。

## 改动

| 改动 | 为什么 |
| --- | --- |
| 429 读 `Retry-After` / 文案里的「Limit resets at」，等到重置再重试（≤5 次），并抬高后续请求间隔 | 配额只有 10 次，不等就等于没测 |
| 模块级节流闸（跨会话共享） | 整套对比每轮新建会话，配额却是整个 Key 共用的 |
| 预算提示按「表单分组数 × 模型 × 提示语 + 1 次自检」算 | 第一版按 `ceil(总字段/批量)` 估成 3 次／轮，实际 7 次／轮，差一倍多 |
| 默认勾选「省配额：只跑中文」 | 全矩阵 29 次请求要等 2 轮配额 |
| `max_tokens` 1024 → 4096、默认批量 8 → 24 | 一批 24 个字段时 1024 会把 JSON 截断 |
| **凡 24 位以上十六进制 / `sk-` 长串一律打码** | 网关在 429 文案里回显密钥裸串，原先只做精确匹配因而漏掉 |

## 安全疏漏（已修，但密钥需轮换）

2.33.0 的错误详情里只做 `detail.split(apiKey).join('***')`。交大网关的 429 文案是
`Rate limit exceeded for api_key: <64 位十六进制>`，用户填入的值若带前缀或空格就匹配不上，
那串密钥因此进了可复制的报告。已改成正则打码。**已告知用户轮换该密钥。**
